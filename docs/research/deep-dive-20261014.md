# 深潜研究：LLM 对抗合规门禁——生成规避样本能力 vs 规则查全上限

- 日期：2026-10-14
- 研究者：自主深潜（AI agent），模型 glm-4-flash（智谱 GLM Coding Plan，OpenAI 兼容端点）
- 仓库：mp-compliance-gate（微信小程序 AI 功能上架合规门禁，Node ≥18 零依赖）
- 研究范式：**对抗研究（adversarial evaluation）**——用真实 LLM 生成「看似合规但藏违规」的小程序样本，批量测量门禁的检出率/逃逸率/误报率；对比「盲生成」与「知规对抗」（把门禁全部规则源码喂给模型）；从逃逸样本反推规则盲区并补齐；再对抗直到撞到能力上限。

## 方法与工具（evidence/deep-dive/）

| 工具 | 作用 |
|---|---|
| `llm.mjs` | GLM API 封装：串行调用 + 全局 ≥2.1s 节流 + 429 退避 60s×3；key 只经环境变量 `GLM_API_KEY`，不落盘 |
| `gen_corpus.mjs <mode> <n> <outdir>` | 生成对抗语料。mode：`blind`（盲生成）/`known`（知规对抗，喂全部规则源码）/`compliant`（试图合规，测误报）。样本 = 可被 runGate 直接扫描的小程序目录 + 同级 `<id>.manifest.json`（模型自报埋雷清单，作 ground-truth 线索，逐条人工核对） |
| `eval_corpus.mjs <corpusDir>` | 离线评测：对每个样本跑 `runGate`，按 manifest 计算违规级召回（per-rule）、样本级逃逸（埋了 blocker 级雷但门禁 0 blocker）、OTHER 类目分布 |

**指标定义**

- 违规级召回（per-rule recall）：manifest 自报在规则 R 范围内埋雷 → 门禁实际报告 R 的比例。
- 样本级逃逸率：埋 ≥1 处 blocker 级违规（AIG01/AIG02/NET01/REG01 范围内）且门禁 0 blocker 的样本占比。BASE01 为 warning，不计入逃逸。
- 全逃逸率：埋雷但门禁 0 finding（连 warning 都没有）。
- 误报率：compliant 语料上门禁报 blocker 的比例。
- **Ground-truth 告示**：manifest 是模型自报，存在「自报不实」（虚报/漏报）可能。所有关键结论（尤其"逃逸"）均逐样本人工核读代码确认，见各轮小节。

复现（key 自备）：

```bash
cd evidence/deep-dive
export GLM_API_KEY=...
node gen_corpus.mjs blind 12 corpus-r1-blind   # 或 known / compliant
node eval_corpus.mjs corpus-r1-blind
```

## 问题链

（按 Q1→Q2→… 顺序在下方追加，每问：假设 / 实验 / 数据 / 结论）


### Q1：盲生成的"藏违规"样本，门禁能拦住多少？（检出结构分析）

**假设**：glm-4-flash 不看规则盲生成时，会自然产出两类违规——粗违规（明文 http、材料 pending）与语义违规（AI 内容不标识）；词表/结构启发式规则拦得住前者、拦不住后者。

**实验**：`node gen_corpus.mjs blind 12 corpus-r1-blind`（temperature 1.0，12 次串行调用）。生成协议本身是一层实验：第一版 JSON-in-JSON 协议 12 次中 4 次结构化输出损坏（字符串内裸换行/截断，`blind-01.raw.txt` 等存档），换成 `===FILE===` 标记协议后解析成功。逐样本人工核读全部 12×5 个文件建立 ground truth（`corpus-r1-blind/_audit-manual.md`），不信任 manifest 自报。

**数据**（人工核读口径，n=12，11 个对抗样本）：

| 规则 | 真实违规数 | 检出 | 召回 | 说明 |
|---|---|---|---|---|
| AIG01（AI 内容界面标识） | 11 | 0 | **0%** | wxml 全用 generic class（container/answer），词表 `ai-chat|ai-result|...` 全不命中 |
| AIG02（复制路径标识） | 0 | — | n/a | 全语料无 `wx.setClipboardData`；manifest 自报 7 处全虚报 |
| NET01（明文/直连） | 10 | 10 | 100% | 2 处自报未命中是模型埋雷失败（写成 https），非漏报 |
| REG01（材料齐备） | 12 | 12 | 100% | blind-06 为"materials 键缺失"结构性触发，消息不准但 blocker 正确 |
| BASE01（云 AI 版本门槛） | 0（范围外） | — | n/a | 无一样本用 wx.cloud.extend.AI；低 libVersion 不在守卫路径 |
| 样本级逃逸 | — | 0/11 | 0% | 每样本都伴随 NET01/REG01 粗违规被拦 |

**结论**：
1. **拦截由粗错误驱动**：0% 逃逸是假安全——每个样本都"顺手"埋了 http/pending 材料这类粗违规；定向看语义违规（AI 内容不标识），召回 0%。
2. **AIG01 的词表法存在查全天花板**：盲生成（非对抗！）的自然命名就 100% 穿透——不需要知道规则也能躲开。
3. **模型侧能力观察**：结构化输出可靠性 8/12（JSON 协议）；埋雷执行力差（blind-12 想埋 http 写成 https，blind-01 谎报明文接口）；manifest 自报虚报率极高（AIG02 虚报 7 处）——**ground truth 必须人工核读**，这条约束贯穿后续所有轮次。

### Q2：知规对抗（把全部规则源码喂给模型）后，绕过成功率如何变化？

**假设**：规则源码即攻击面地图。知道 `pc.setting.urlCheck` 只读顶层、AIG01 只认 ai-* 词表、AIG02 只扫 7 行窗口后，模型应能定向构造 0-blocker 样本；但小模型可能"知道却做不到"。

**实验**：`node gen_corpus.mjs known 12 corpus-r2-known`——prompt 内嵌 rules-meta.yaml + 5 条规则全部源码，角色设定为红队工程师，要求埋真实违规且尽量绕过门禁。11/12 样本有效（1 个标记解析失败）。逐样本人工核读。

**数据**（人工核读口径，n=11；原始对照见 `corpus-r2-known/_eval.json` / `_eval-patched.json`）：

| 规则 | 自报埋雷 | 真实埋雷 | 打补丁前检出 | 手法 |
|---|---|---|---|---|
| AIG01 | 9 | 9 | 8/9（89%）| 唯一逃逸 known-01 用 generic class（chat/message）——**规则源码在手，模型仍无法稳定放弃 "ai-" 命名引力**：8 个样本自己写出了 ai-chat/ai-answer 等词表命中项 |
| AIG02 | 8 | 4（其余为虚报） | 3/4 | known-06 真合规（data 内模板串含 AI_LABEL）；known-12 写了「人工智能生成内容」变体文案（真标识，词表漏认→假阳性）；known-10 复制的是用户输入而非 AI 内容（语义不可判定→可接受的人工确认项） |
| NET01 | 9 | 2 | **0/2** | **嵌套规避全部成功**：urlCheck:false 藏进 `miniprogram.setting`（known-03 还叠加 `// 注释` 使整个 JSON 解析失败→配置全盲）；其余样本全部改用 https——知规后无人再写明文 http |
| REG01 | 9 | 9（其中 4 个伪造 all-ready） | 9/9（**但 4 个是解析事故的假拦截**） | known-03/08/09/12 把 status 全写 ready（语义层伪造成功）；其中 03 因 0 缩进 list、08 因尾部 ``` 围栏触发 yaml 解析失败被「误打误撞」拦下，消息还是错的（"缺少清单文件"） |
| BASE01 | 8 | 0（无云 AI 调用） | — | known-03 嵌套层藏 libVersion 3.15.0（<3.15.1），但无 wx.cloud.extend.AI 使用→规则不触发（范围外） |
| 样本级逃逸 | | | 0/9 | 每样本仍被 ≥1 blocker 拦（多为解析事故或剩余粗违规） |

**结论**：
1. **知规 → 定向结构规避**：NET01 的 urlCheck 子检查被 100% 绕过（嵌套 + JSON 注释两连）；REG01 被语义伪造（all-ready）绕过，当时的"拦截"全是 yaml 解析事故，属于**假安全**。
2. **知规 ≠ 能执行**：AIG01 词表就写在 prompt 里，8/9 样本仍因 "ai-" 命名引力被词表命中——glm-4-flash 能指出绕法（known-01）但不能稳定执行绕法。
3. **新发现的可修缺陷**（→Q3）：①嵌套 project.config.json 致 urlCheck/libVersion 不可见；②JSON 解析失败静默置 null（配置类规则全盲）；③yaml-lite 不认标准同缩进列表；④checklist 解析失败被误报为"缺少文件"；⑤AIG02 窗口内任意位置出现标识变量即假通过（诱饵）；⑥AIG01 词表无结构兜底。

### Q3：补齐 5 条绕过路径后，检出率恢复到多少？

**修复**（全部带回归测试 `tests/adversarial-hardening.test.mjs`，11 个用例逐一对应上述手法）：

1. `engine.mjs`：project.config.json 平铺/`miniprogram` 嵌套统一解析（setting 合并、libVersion 取并集）；解析失败显式暴露 `projectConfigError`（不再静默 null）。
2. `yaml-lite.mjs`：支持标准 YAML 同缩进列表（`key:` 下一级 list 与 key 同缩进）；顶层游离行仍显式报错（不静默丢弃，守住 OB-3 的严格性承诺）。
3. `NET01`/`BASE01`：配置解析失败 → 「需人工确认」finding（宁可疑不误断，OB-1 原则）。
4. `REG01`：区分「文件缺失」与「文件存在但解析失败」两种消息。
5. `AIG01`：新增页映射结构判定——app.json pages → 页 js/wxml 配对，「强信号（AI API/词表命中）或双中信号（ai 路径 + AI 业务文案）」判定 AI 页后要求标识；app.json pages 结构异常显式交人工。
6. `AIG02`：判定范围从 7 行窗口收紧到 data 表达式本身（截断到 success/fail 回调前）；标识词表扩充「人工智能生成 / AI generated」。

**数据**（同两套语料重放，`_eval-patched.json`）：

| 指标 | 补丁前 | 补丁后 |
|---|---|---|
| AIG01 盲语料召回 | 0/11（0%） | 10/11（91%） |
| AIG01 知言语料召回 | 8/9 | 9/9（100%） |
| NET01 urlCheck 嵌套规避 | 0/2 检出 | 2/2 检出 |
| REG01 假拦截（错消息） | 4 | 0（消息正确区分缺失/解析失败） |
| AIG02 假通过（诱饵）/假阳性（变体文案） | 存在 | 关闭 |
| 离线测试 | 15/15 | 26/26 |

**残余**（人工核读确认）：
- blind-07 仍逃逸 AIG01：app.json 是数组包裹的畸形结构 + pages 为字符串 → 已加「pages 字段非数组」人工确认 finding，页级结构判定对其不生效（畸形输入的极限：只能转人工，不能臆断）。
- known-09 语义伪造 all-ready 成功：checklist 是自证材料，静态门禁无法核实现实世界材料真伪——**规则查全的固有上限**（REG01 只能保证"清单被跟踪"，不能保证"清单为真"）。

### Q4：对补齐后的门禁再打一轮知规对抗，模型还剩几条路？

**假设**：把补丁后的规则源码再次喂给模型（gen_corpus 运行时实时读 src/rules/），其规避手段应收敛到规则的理论盲区（自证材料伪造），而不是无限猫鼠。

**实验**：`node gen_corpus.mjs known 12 corpus-r4-known-v2`（9/12 有效，3 个标记解析失败）。

**数据**（人工核读）：

- **NET01：0 处真实违规**。全语料无 http://、全部 urlCheck:true——模型读过新源码后**主动放弃**了已封死的路径（嵌套/注释在 Q3 已修，明文 http 在 Q2 就已弃用），改走 `wx.cloud.callFunction`（微信官方认可的网络通道，本就不该报）。
- **AIG02：0 处真实违规**（无 setClipboardData——同样弃用）。
- **AIG01：9/9 全部检出**（词表或结构判定命中）。模型连「去掉 ai-* class」这一步都仍然做不到（与 Q2 相同的命名引力）。
- **REG01：4/12 语义伪造 all-ready 成功逃逸**（known-02/06/07/10，如 known-10 四项材料全 ready 但 id 换成了自造名）。这是 Q3 已确认的自证材料固有盲区——**静态门禁无法核验现实世界材料真伪**。
- 样本级逃逸 0/9：每个伪造 checklist 的样本都还带着被 AIG01 拦下的真违规。

**结论**：一轮加固后，glm-4-flash 的知规对抗面收敛到**唯一车道：REG01 自证伪造**。这条车道不是实现缺陷，而是「清单 ≠ 事实」的规则论上限——堵死它需要外部事实源（工商数据/备案库 API），超出零依赖静态门禁的能力边界。

### Q5：合规意图的生成样本上，门禁误报率多少？（精度面）

**假设**：结构启发式（AIG01 页映射）和词表扩充可能引入误报；合规生成是天然的反例语料。

**实验**：`node gen_corpus.mjs compliant 8 corpus-r5-compliant`。注意"合规意图"≠"合规事实"——模型被要求全绿，产出仍需人工核读。

**数据**（人工核读）：

| 现象 | 计数 | 定性 |
|---|---|---|
| REG01 状态词表误报（Checked/Completed/passed/compliant/已就绪 ≠ 字面 ready） | 7/8 | **真误报**（已修：就绪词表归一化 → 0） |
| NET01 urlCheck:false | 4/8 | **真阳性**——模型"想合规"却写了 urlCheck:false（开发者工具常见坏习惯被模型学去了） |
| AIG02 复制路径无标识 | 2/8 | **真阳性**——指令要求追加标识，代码没加 |
| AIG01 结构判定误报 | 0/8 | 无 |
| 全绿样本 | 3/8（修复后） | 01/04/05 |

**结论**：修复后合规语料 **0 误报**；更有意思的是 **6/8 的"合规意图"样本含真实违规**——与 Q2 的"对抗意图却写出可检出模式"互为镜像：glm-4-flash 的意图→代码执行层存在系统性损耗，方向无关。

### Q6：给模型精确的"洗白配方"，能否产出静态不可检的违规 AI 页？

**假设**：Q2/Q4 中模型不重命名 ai-* class 是"命名引力"（能力不足）；若给出逐步配方（中性路径/中性 class/中性接口名/无 AI 词），模型应能执行——此时词表/结构启发式将全部失效，即规则查全的理论下限。

**实验**：`node gen_laundered.mjs 8 corpus-r6-laundered`——prompt 逐步给出洗白要求（含 urlCheck:true、材料 all-ready，唯一违规点=AI 回答无标识）。

**数据**（人工核读 + 定向 grep）：

- **AIG01 洗白成功 7/8**：pages/chat/chat、class=message/answer、接口 /q /message，全部 AI 词汇（AI/智能/大模型/llm/gpt/model）零残留；仅 laundered-03 留下可检出信号。**给出配方后模型执行完美**——Q2/Q4 的"做不到"确系自主能力不足，非硬限制。
- checklist 结构大混乱：8 个样本 6 种 schema（materials 列表 / items 列表 / 顶层数组 / 名称→status 映射 ×2 / `-名称:` 畸形 ×2 / 外加 markdown 围栏）。已让 REG01 接受三种"列表语义"变体；映射与畸形保持 fail-closed（blocker + 明确提示结构约定），不静默放行。
- 洗白后全链路违规样本（AI 无标识 + 材料 all-ready 伪造）**2/8 完全穿透门禁**（laundered-01/06，0 blocker）。

**结论**：**辅助对抗（人给配方）完全成功，自主对抗（模型自己找路）在加固后归零**。静态门禁对"零信号 AI 页"在原理上不可检——对无 AI 特征的页面强制标识要求会把误报打到天上。该防线的归属是平台侧（运行时行为、类目人工审、举报），不是静态扫描器。

### Q7：全部 59 次 LLM 调用的可靠性统计（模型侧瓶颈定量）

**数据**（全部调用日志见各轮 console 输出与 `_index.json`/`*.raw.txt` 存档）：

| 指标 | 数值 |
|---|---|
| 总调用 | 59（盲 19 / 知规 r2 12 / 知规 r4 12 / 合规 8 / 洗白 8） |
| 结构化输出失败（JSON-in-JSON 协议，r1 主批） | 4/12（33%）——裸换行进字符串、伪截断 |
| 结构化输出失败（===FILE=== 标记协议，r2-r6 主批） | 4/40（10%；盲批另有 3 次失败系我方解析器过严，升级多数组 manifest 解析后可恢复，不计模型账） |
| manifest 自报虚报（以人工核读为准） | AIG02 幻报 7 处（r1）；BASE01 范围外自报 ~20/23；模板占位符 manifest 2 份 |
| 埋雷执行失败 | 想埋 http 写成 https（blind-12）、谎报明文接口（blind-01）、合规要求 urlCheck:true 却写 false（4/8） |
| 自主规避执行（知道词表仍写 ai-* class） | r2 8/9、r4 9/9 被 "ai-" 引力捕获 |

**结论**：glm-4-flash 的对抗能力瓶颈不在"知识"而在**执行**——指令细节稍多（schema、枚举单选、命名约束）就出现 10-33% 的格式失败与高频语义偏移；这同时解释了 Q2（对抗意图→执行不出）与 Q5（合规意图→执行不全）。工程上不可通过 prompt 修复（本轮 prompt 已含格式示范与逐项纠正）。

## 瓶颈结论（停止条件达成：Q5/Q6/Q7 收敛到同一组能力上限）

**一句话**：规则侧的真实查全上限 = 「自证材料不可核验」+「零静态信号 AI 页不可检」两条原理性盲区；模型侧的真实能力上限 = 「意图→代码执行损耗」（格式失败 10-33%、语义偏移高频），使**自主**对抗在加固后归零、但**辅助**对抗（人给配方）可 100% 穿透——静态门禁对后者原理性失明，防线在平台运行时与人工审核侧。

**证据复现**：

```bash
cd evidence/deep-dive
node eval_corpus.mjs corpus-r1-blind        # 盲语料（补丁前 AIG01 召回 0/11，补丁后 10/11）
node eval_corpus.mjs corpus-r2-known        # 知规对抗 r2（嵌套 urlCheck 绕过现场）
node eval_corpus.mjs corpus-r4-known-v2     # 补丁后再对抗（规避面收敛到 REG01 伪造）
node eval_corpus.mjs corpus-r5-compliant    # 合规意图（修复后 0 误报）
node eval_corpus.mjs corpus-r6-laundered    # 定向洗白（laundered-01/06 全穿透）
npm test                                     # 27/27 绿（含 12 条对抗回归）
```

原始样本与逐轮审计：`evidence/deep-dive/corpus-*/`（含 `_eval*.json` 机器结果与 `_audit-manual.md` 人工核读）。
